# 01 · 结构化输出为什么难

> 读完这篇你能回答：为什么"让模型输出 JSON"看起来简单、实际上要四层才稳。

## 0. 先破除一个幻觉

很多人以为结构化输出是"提示词里写一句『请输出 JSON』"。
真实情况是：**你是在要求一个概率模型遵守形式语言，而它只学过"像 JSON 的文本"。**

它学会的是"统计上像什么"，不是"语法上必须是什么"。所以会出现十几种坏法：

| # | 坏法 | 例子 | 层次 |
|---|---|---|---|
| 1 | 外面包代码围栏 | ` ```json {...} ``` ` | 语法 |
| 2 | 前后加客套话 | `好的，结果如下：{...} 希望有帮助` | 语法 |
| 3 | 单引号代替双引号 | `{'a': 1}` | 语法 |
| 4 | 尾随逗号 | `{"a": 1,}` | 语法 |
| 5 | 键名不加引号 | `{a: 1}` | 语法 |
| 6 | Python 字面量 | `{"a": True, "b": None}` | 语法 |
| 7 | 全角标点 | `{“a”：1}` | 语法 |
| 8 | 字符串里有裸换行 | `{"a": "第一行\n第二行"}` | 语法 |
| 9 | 被 `max_tokens` 截断 | `{"a": 1, "b": {"c":` | 配置 |
| 10 | 类型不对 | `{"age": "未知"}` | 语义 |
| 11 | 枚举值不在范围内 | `{"currency": "RMB"}` | 语义 |
| 12 | 多了不该有的字段 | `{"a": 1, "note": "..."}` | 语义 |

**关键观察：前 8 种是语法问题，第 10-12 种是语义问题，第 9 种是配置问题。**
三类问题的解法完全不同 —— 这就是为什么"只用一种手段"永远不够。

## 1. 四种解法各自的射程

```
                    语法问题        语义问题       截断问题
提示词约束            ⚠️ 弱          ❌ 无          ❌ 无
JSON 模式             ✅ 强          ❌ 无          ❌ 无
强制 function call    ✅ 强          ⚠️ 部分        ❌ 无
强解析层              ✅ 强          ❌ 无          ⚠️ 部分
校验 + 反馈修复        ➖ 不需要       ✅ 强          ❌ 无
约束解码（vLLM 等）    ✅ 最强        ⚠️ 可做        ❌ 无
```

四个必须记住的结论：

1. **JSON 模式和强解析层是替代品，不是补充品。** 它们都在解决"语法"，你只需要一个。
2. **强制 function call 有一点语义约束力**，因为 schema 里的
   `additionalProperties: false` 会直接限制模型能产生哪些字段。
   但它管不住"枚举值编错"和"类型写错"。
3. **只有"校验 + 把错误回灌"能治语义问题。** 因为语义错误需要模型重新理解任务，
   而不是重新格式化。
4. **截断谁都治不了。** 那是 `max_tokens` 太小，属于参数配置。
   看到一个团队用"重试"去修截断，就知道他们没做归因分析。

## 2. 为什么错误信息必须带路径

假设 schema 是 `{"order_id": ..., "amount": ..., "currency": {"enum": [...]}}`，
模型输出了 `{"currency": "RMB"}`。两种回灌方式：

```
A: 输出不符合 schema，请重新生成。
B: 校验失败：
   - $.currency: 取值必须是 ['CNY', 'USD', 'EUR'] 之一，实际 'RMB'
```

A 的效果：模型重生成一遍，很可能还是 RMB（因为它不知道哪里错了）。
B 的效果：模型知道了"currency 这个字段只允许三种值"，改对概率很高。

**在 Agent 系统里，错误信息是 prompt 的一部分，不是日志。**
所以要写清：哪个字段（`$.currency`）、期望什么（enum 列表）、实际是什么（`RMB`）。

这也是我坚持"错误要带 JSON 路径"而不是"报个错就行"的原因。

## 3. 一个容易被忽略的坑：纠偏会掩盖问题

模型的常见手滑是"把数字写成字符串"：

```json
{"age": "23"}     ← 期望 integer
```

把 `"23"` 自动纠偏成 `23` 是合理的、省事的、也是**危险**的。

危险在哪？在**评测**里。
我第一版把"类型错误"这条评测样本写成 `"age": "23"`，结果校验器的纠偏把它救回来了，
这条样本就再也测不出"语义错误需要反馈修复" —— 表面上成功率变好看了，
实际上你失去了一个观测点。

**这就是为什么评测样本要设计成"纠偏救不回来"的形态**（现在用的是 `"age": "未知"`）。
推论：`coerce=True` 是个便利特性，但在评测场景里应该关掉，或者至少两种都跑一遍。

## 4. 约束解码：从"事后修复"到"事前约束"

前面说的都是**事后**手段：模型说完了，我再修。

**约束解码**（vLLM 的 guided decoding、Outlines、llama.cpp 的 GBNF、
OpenAI 的 Structured Outputs）是**事前**手段：在每一个 token 采样前，
把会让 JSON 变非法的 token 概率直接置零。

它依赖一个判定：

> 当前已经生成的这段文本，还有可能被补成一个合法的 JSON 吗？

三种状态：

| 状态 | 含义 | 处理 |
|---|---|---|
| `complete` | 已经是完整 JSON | 可以停 |
| `viable` | 还没完，但存在合法补全 | 继续生成 |
| `invalid` | 不可能补成合法 JSON | 砍掉这条分支 |

`grammar.py` 用递归下降解析器实现这个判定：输入用完但语法没结束 → `_Incomplete`；
语法真的错了 → `_Invalid`。两者的区分就是这个模块的全部价值。

**它治不了什么**：`{"age": "未知"}` 在它眼里语法完全合法。
要把 schema 也压进采样，需要把 JSON Schema 编译成状态机（Outlines 的做法），
这是另一个量级的工程。所以业界现在的实践是**两层叠加**：

```
约束解码（保证语法合法）+ schema 校验与反馈（保证语义正确）
```

## 5. 什么时候该用哪一层

| 场景 | 建议 |
|---|---|
| 自己控制推理服务（vLLM / llama.cpp） | 上约束解码，语法问题一次性归零 |
| 用云 API，模型支持 Structured Outputs | 用，但**仍然要自己校验语义** |
| 用云 API，模型只支持 json_object | JSON 模式 + 自己的校验层 |
| 模型什么都不支持（老模型 / 本地小模型） | 强解析层 + 反馈修复 |
| 任何情况 | **都要有自建评测集**，否则你不知道改完是变好还是变坏 |

最后一行是重点：**没有评测的结构化输出优化，都是感觉驱动的。**
