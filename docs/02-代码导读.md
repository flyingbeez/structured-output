# 02 · 代码导读

> 七个模块，按依赖顺序读。先读 `samples.py`，因为它定义了"什么叫坏"。

## 0. 先看实验设计

```
samples.py   20 条样本，坏法手工标注
      │       8 干净 / 8 结构性 / 3 语义性 / 1 截断
      ▼
llm.py       确定性模拟器：按 (样本 id, 模式, 轮次) 产出对应坏法的文本
      │       json / tool 模式会"修好"结构性坏法 —— 模拟真实的格式约束效果
      ▼
strategies.py  六种策略 = (mode × parser × rounds) 的组合
      │
      ├──► extract.py   文本 → 对象（六条降级路径）
      ├──► schema.py    对象 → 是否合法（带 $.path）
      └──► 校验失败 → 把 error_text 回灌 → 下一轮
      ▼
bench.py     汇总成对照表 + 按坏法分解
```

**这个设计的核心是：把"模型行为"和"我的处理逻辑"解耦。**
评测结果里 `naive` 和 `extract` 的差距，100% 归因于解析层，没有别的变量。

## 1. `samples.py` —— 定义"什么叫坏"

`apply_defect(sample)` 把一个正确输出变成带指定坏法的文本：

```python
if defect == "fenced":        return f"```json\n{js}\n```"
if defect == "single_quotes": return js.replace('"', "'")
if defect == "trailing_comma":return js[:-1] + ",}"
if defect == "bare_keys":     return re.sub(r'"(\w+)"(\s*:)', r"\1\2", js)
if defect == "truncated":     return js[: int(len(js) * 0.6)]
```

语义性坏法改的是值，语法仍然合法：

```python
if defect == "wrong_type":
    mutated[sample.defect_field] = "未知"   # 刻意用纠偏救不回来的值
```

**这里有个我踩过的坑**（README 里也写了）：一开始写的是 `str(mutated[field])`，
即 `23 → "23"`。结果 `schema.py` 的 `coerce` 把它悄悄改回 23，这条样本就没用了。
**评测样本必须设计成"你的兜底逻辑救不回来"的形态，否则你测的是兜底逻辑，不是模型。**

## 2. `extract.py` —— 六条降级路径

```python
extract_json(text)
  ① direct          json.loads 直接成功
  ② strip_fence     去掉 ```json 围栏再试
  ③ balanced_span   扫描平衡括号片段（正确跳过字符串内部）
  ④ text_repair     全角标点 / Python 字面量 / 单引号 / 裸键名 / 尾逗号 / 注释
  ⑤ repair_span     修复后再截取片段
  ⑥ close_truncated 补齐未闭合的括号和引号
```

两个值得注意的实现细节：

**括号扫描必须跳过字符串内部**：

```python
def _iter_balanced_spans(text):
    in_string = False; escaped = False
    for index, ch in enumerate(text):
        if in_string:
            if escaped: escaped = False
            elif ch == "\\": escaped = True
            elif ch == '"': in_string = False
            continue
        ...
```

否则 `{"a": "}{"}` 会被切成两半。这个 bug 有专门的测试
（`test_brace_inside_string_not_confused`）。

**文本修复是"尽力而为"，会记 notes**：每做一次修改就记一条，
既方便调试，也方便统计"哪种修复路径最常命中"。

## 3. `schema.py` —— 约束要真的执行

`_validate` 是递归的，每层把 `path` 往下带：

```python
value = [_validate(item, schema["items"], path + [i], errors, coerce=coerce)
         for i, item in enumerate(value)]
```

所以错误能报到 `$.nums[1]` 这个精度。三类结构分别处理：标量 / 数组（下标）/ 对象（点号）。

**组合关键字**：`allOf` 顺序应用，`anyOf` 任一通过，`oneOf` 必须恰好一个。
`test_one_of_rejects_matching_both` 盯的是 `oneOf: [integer, number]` 这种
"3 同时满足两个分支"的情况。

**纠偏的边界**（`_coerce`）：

```python
if wanted == "integer" and isinstance(value, str):   # "5" → 5  值得救
if wanted == "string" and isinstance(value, (int, float, bool)):  # ✗ 刻意不做
```

第二条是刻意不做的，理由见 docs/01 第 3 节。

**`schema_is_sane()`**：检查 schema 自己有没有写错
（`minimum > maximum`、`required` 里的字段不在 `properties` 里、空 `enum`）。
面试常问"schema 本身会不会是 bug 源"——这是答案。

## 4. `grammar.py` —— 约束解码原理

不用显式状态机，而是让递归下降解析器区分两种失败：

```python
class _Incomplete(Exception):  # 输入用完但语法没结束 → 可行前缀
class _Invalid(Exception):     # 语法真的错了 → 砍掉这条分支
```

`parse_value` 遇到输入末尾就抛 `_Incomplete`，遇到非法字符就抛 `_Invalid`：

```python
def parse_value(self):
    self._skip_ws()
    ch = self._peek()
    if ch == "":            raise _Incomplete()
    if ch == "{":           self.parse_object()
    elif ch == "t":         self._expect_literal("true")   # 内部逐字符比对
    else:                   raise _Invalid(f"值不能以 {ch!r} 开头")
```

数字解析要特别小心 —— 我第一版让 `-` 和 `12.` 都判成了 `complete`，
这是错的：

```python
digits = 0
while ...isdigit(): digits += 1
if digits == 0:
    if self.pos >= len(self.text): raise _Incomplete("数字还没有整数部分")  # 只有 '-'
    raise _Invalid("数字必须以数字开头")
if self._peek() == ".":
    self.pos += 1
    if self.pos >= len(self.text): raise _Incomplete("小数点后还没有数字")  # '12.'
```

`allowed_tokens(prefix, vocab)` 用**暴力试一遍**实现 token 掩码。
真实系统里这是 O(1) 的状态机转移，这里为了可读性牺牲了效率 ——
反正词表只有十几个 token。

## 5. `strategies.py` —— 三个正交开关

六个策略不是六段代码，而是三个参数的组合：

```python
@dataclass(frozen=True)
class Strategy:
    key: str
    mode: str      # text | json | tool   —— 请求侧要不要加格式约束
    parser: str    # naive | extract     —— 客户端要不要修复
    rounds: int = 1                       # 要不要把错误回灌重试
```

**这是这个项目最值得学的一点**：把"六种做法"重构成"三个维度"，
对照实验才能做干净（每次只变一个维度）。

`run()` 的循环结构：

```python
for round_no in range(1, strategy.rounds + 1):
    completion = llm.complete(..., mode=strategy.mode,
                              meta={"sample_id": sample.id, "round": round_no})
    parsed_ok, value, method, parse_error = _parse(strategy, completion.text)
    if not parsed_ok:
        last_error = parse_error
    else:
        check = validate(value, sample.schema)
        if check.ok:  return result            # 成功
        last_error = check.error_text()
    user = build_repair_prompt(sample, previous_output, last_error)   # ← 关键
```

`build_repair_prompt` 把**上一轮输出 + 精确错误 + schema** 一起回灌。
示例 02 会把这个 prompt 打印出来。

## 6. `llm.py` —— 模拟器是可信度的基石

```python
if round_no > 1:
    effective = "truncated" if defect in UNFIXABLE_DEFECTS else "clean"
elif mode in ("json", "tool") and defect in STRUCTURAL_DEFECTS:
    effective = "clean"
elif mode == "tool" and defect == "extra_field":
    effective = "clean"
else:
    effective = defect
```

这段逻辑编码了真实世界的经验：
- **格式约束能治语法，治不了语义**；
- **收到精确错误后模型通常能改对**，除了物理上修不了的截断；
- **`tool` 模式多治一个"多余字段"**，因为 schema 约束了字段集合。

`OpenAICompatLLM` 展示了三种模式的请求差异：

```python
if mode == "json":  body["response_format"] = {"type": "json_object"}
elif mode == "tool":
    body["tools"] = [{"type": "function", "function": {"name": "emit_result",
                                                      "parameters": schema}}]
    body["tool_choice"] = {"type": "function", "function": {"name": "emit_result"}}
```

**`tool_choice` 强制调用 + 从 `tool_calls[0].function.arguments` 取值**，
是 Structured Outputs 普及之前最可靠的格式约束手段 —— 面试常问。

## 7. 测试思路

| 测试 | 验证什么 |
|---|---|
| `test_brace_inside_string_not_confused` | 括号扫描要跳过字符串内部 |
| `test_every_defect_changes_the_text` | 每条坏法样本确实和正确答案不同（防"样本写错了还测得很开心"） |
| `test_truncation_defeats_every_strategy` | **反向案例**：截断在所有策略下都必须失败 |
| `test_json_mode_and_extractor_are_substitutes` | **核心结论**：两者成功率相等 |
| `test_parser_is_the_biggest_single_win` | 解析层收益 ≥ 30pp 且不增加尝试次数 |
| `test_no_strategy_is_perfect` | **诚实性测试**：修复循环也不能是 100% |
| `test_number_is_not_silently_stringified` | 纠偏不能反向掩盖类型错误 |
| `test_every_allowed_token_keeps_prefix_viable` | 掩码的不变式 |
| `test_benchmark_is_deterministic` | 跑两遍结果完全一致 |

`test_no_strategy_is_perfect` 是我最想保留的一条：
如果哪天有人把样本改成让它 100%，这个测试会失败，逼他重新想清楚
"是不是把修不了的样本删掉了"。

## 8. 建议的动手练习

1. **换成你自己的 schema**：把 `samples.py` 的 4 个 schema 换成你业务的真实结构，
   跑一遍看成功率变化。
2. **加第七种策略**：`small_model_repair` —— 校验失败时换一个更小的模型来修，
   量一下成本和成功率的交换比。
3. **把 coerce 也作为一个维度**：`coerce=True/False` 各跑一遍，
   看纠偏到底"救了"多少、又"掩盖"了多少。
4. **接真实模型**：`python examples/03_strategy_benchmark.py --live`，
   把结果和模拟器对照。**这是最有价值的一步**，因为你会发现真实分布和模拟的不一样。
5. **把 grammar 接进生成循环**：写一个 demo，用 `allowed_tokens` 去约束一个
   玩具语言模型的采样，直观感受约束解码。
