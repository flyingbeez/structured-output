# 03 · 围绕本项目的面试问答

> 这个项目的价值不在"我会用 Pydantic"，而在于**你能拿出一张自己跑出来的对照表，
> 并解释清楚每一行数字背后的机制**。这是"做过"和"看过教程"的分界线。

---

## A 类 · 核心结论（最容易被追问）

### A1. 你这个项目在做什么？

> 结构化输出的建议满天飞——开 JSON 模式、用 function calling、上 Pydantic、加校验重试。
> 但很少有人量化过这些手段各自值多少。
>
> 我搭了一个评测：20 条抽取样本，坏法是**手工标注**的（8 条干净、8 条语法坏、3 条语义坏、
> 1 条被截断），跑 6 种策略。结论是：**最大的收益来自客户端的解析层，而且不花钱** ——
> 从 40% 提到 80%，平均尝试次数还是 1.00，因为不需要额外请求。
>
> 更有意思的是 JSON 模式和强解析层**打平在 80%**，说明它们解决的是同一类问题（语法），
> 是替代关系不是叠加关系。而语义错误只能靠校验 + 反馈修复，能到 95%，代价是 token ×1.28。

### A2. 为什么 JSON 模式和强解析层是替代关系？

> 因为它们的目标都是"让这段文本能被解析成 JSON 对象"。
> JSON 模式是在**请求侧**让服务端保证语法合法；强解析层是在**客户端**把不合法的情况修回来。
> 一个上游做、一个下游做，做的是同一件事。
>
> 我的数据里两者都是 80%，而且叠加起来（`json_extract`）还是 80% ——
> 这就是"没有叠加收益"的直接证据。
>
> 反过来，如果你只有一个 `json.loads`，JSON 模式的收益非常大（40% → 80%）。
> 所以选哪个取决于你的解析层有多强，不是取决于哪个"更高级"。

### A3. 那 20% 的失败是怎么剩下的？

> 全是**语义问题**：类型不对、枚举值编错、多了不该有的字段。
> 语法层面它们完全合法 —— `{"currency": "RMB"}` 是合法 JSON，只是 RMB 不在
> `enum: ["CNY","USD","EUR"]` 里。
>
> 这类问题**格式约束治不了**，因为格式约束只管"是不是合法 JSON"。
> 唯一有效的手段是校验后发现错、把精确的错误信息回灌给模型让它重新理解任务。
>
> 加到 `repair_loop` 后成功率 95%，唯一没救回来的是**被 max_tokens 截断**那条 ——
> 那是参数配置问题，重试多少次都没用。

### A4. 为什么截断救不回来？

> 因为截断的根因不在模型"不愿输出完"，而在 `max_tokens` 设小了。
> 你重试十次，它还是会在同一个位置被切掉。
>
> 正确做法是：换算出够用的 `max_tokens`，或者让模型分段输出。
> 我在评测里保留这一条失败样本，是因为**删掉它就能把成功率凑到 100%，
> 但那是自欺欺人** —— 我还专门写了一个测试 `test_no_strategy_is_perfect` 盯着这件事。

## B 类 · 解析层（工程细节）

### B1. 模型返回的 JSON 到底会有哪些坏法？

> 我整理出 12 种。前 8 种是语法层面的：` ```json ` 围栏、前后客套话、单引号、
> 尾随逗号、裸键名、Python 字面量（`True`/`None`）、全角标点、字符串里的裸换行。
> 第 9 种是被截断。后 3 种是语义层面的：类型错、枚举值错、多余字段。
>
> 这个分类很重要，因为**不同类别的解法完全不同**。语法靠解析或约束，
> 语义靠校验反馈，截断靠改配置。

### B2. 解析器为什么要做成"降级路径"而不是一个正则？

> 因为每条路径都有它覆盖不了的情况，硬要用一条路径解决就会越写越脆。
> 我是六条，从严格到宽容：
> 直接 `json.loads` → 去围栏 → 扫描平衡括号片段 → 文本级修复 → 修复后截片段 → 补齐截断。
>
> 好处是：**每条路径的成功率可以分别统计**，你就知道该优化哪一条。
> 这也是我在 `ExtractionResult` 里带 `method` 字段的原因。

### B3. "扫描平衡括号"有什么坑？

> 必须跳过字符串内部。`{"a": "}{"}` 这种输入，如果只用括号计数会切错位置。
> 实现上要维护 `in_string` 和 `escaped` 两个状态。
> 这个 bug 我有专门的测试盯着（`test_brace_inside_string_not_confused`）。
>
> 另外还有单引号的情况：`{'a': '}'}` —— 我的扫描只认双引号，所以这种会失败。
> 这是已知局限，写在我的局限清单里。

### B4. 文本级修复会不会改坏语义？

> 有风险，所以我限定了几条保守规则：
> - 单引号→双引号**只在文本里完全没有双引号时**才做（避免破坏内部的引号）；
> - 尾随逗号只在 `,}` / `,]` 前删除；
> - Python 字面量只在词边界上替换。
>
> 但这不是完备的解法。比如字符串内部本身含双引号，我的修复就无能为力 ——
> 这也是为什么**生产环境应该优先用 schema 约束（function calling / Structured Outputs）
> 而不是靠正则修**。解析层是兜底，不是主力。

## C 类 · 评测设计（最能体现工程素养）

### C1. 你为什么用模拟器而不是直接用真实模型？

> 因为评测要能当**回归门禁**用。真实模型的评测有三个致命问题：
> 每次数字都不一样（没法判断改动是变好还是变坏）、要花钱、还可能因为限流跑不完。
>
> 模拟器把"模型行为"变成可编程的依赖，跟单元测试里 mock 掉网络请求是同一个思路。
>
> **但我必须说清楚它的边界**：模拟器证明的是"我的解析/校验/修复逻辑是否正确处理了
> 这 12 类坏法"，**不能**证明"真实模型有 40% 概率输出坏 JSON"。
> 所以同一个脚本支持 `--live`，对真实模型跑同一套流程，结论以后者为准。

### C2. 你怎么保证评测样本本身是有效的？

> 有几条防线：
> 1. `test_every_defect_changes_the_text` —— 保证每条坏法样本确实和正确答案不同，
>    防止"样本写错了但测试还全绿"；
> 2. 坏法分布是**设计**出来的，不是随机的。随机坏法混在一起你只知道总体成功率，
>    不知道哪一类没兜住；
> 3. `test_benchmark_is_deterministic` —— 跑两遍结果必须完全一致。
>
> 还有一次真实的教训：我一开始把"类型错误"样本写成 `"age": "23"`，
> 结果校验器的类型纠偏把 `"23"` 改回了 `23`，这条样本就失效了。
> **评测样本必须设计成"你的兜底逻辑救不回来"的形态**，否则你测的是兜底逻辑，不是模型。

### C3. 按坏法分解为什么比总体成功率重要？

> 因为总体成功率只告诉你"好不好"，分解才告诉你"哪里不好、该改什么"。
>
> 比如我的表里 `tool_call` 比 `extract` 高 5 个百分点，分解后能看出**全部来自"多余字段"**
> 这一类 —— 因为 function call 的 schema 里 `additionalProperties: false` 约束了字段集合。
> 如果没有分解，我只知道"tool_call 好一点"，不知道该不该为它付出迁移成本。

### C4. 你会怎么把这个评测用到真实业务上？

> 三步：
> 1. **换成真实 schema**：把我那 4 个示例 schema 换成业务里的真实结构，
>    坏法分布要按线上日志统计，而不是我这种"均匀设计"；
> 2. **接进 CI**：每次改提示词或换模型都跑一遍，成功率下降就阻断合并；
> 3. **同时看成本**：我的表里有"相对基线 token"一列。
>    修复循环把成功率从 80% 提到 95%，代价是 token ×1.28 —— 这个买卖划不划算
>    取决于业务对错误率的容忍度和单价。

## D 类 · 约束解码（加分项）

### D1. 你知道 Structured Outputs 是怎么实现的吗？

> 本质是**约束解码**：在每一个 token 采样前，把会让 JSON 变非法的 token 概率置零。
> 依赖一个判定："当前这段前缀还有可能被补成合法 JSON 吗？"
>
> 我用一个递归下降解析器实现了这个判定（`grammar.py`），三种状态：
> `complete`（已是完整 JSON）、`viable`（还能补完）、`invalid`（不可能补完）。
> 关键是区分后两者：输入用完但语法没结束 → viable；语法真的错了 → invalid。
>
> 然后 `allowed_tokens(prefix, vocab)` 就是"把候选 token 逐个试一遍，留下可行的"。
> 真实系统里这是 O(1) 的状态机转移，我用暴力是为了可读性。

### D2. 约束解码能替代 schema 校验吗？

> **不能。** 约束解码只保证语法。`{"age": "未知"}` 在它眼里完全合法，
> 但不符合 `{"age": {"type": "integer"}}`。
>
> 要把 schema 也压进采样，需要把 JSON Schema 编译成状态机（Outlines 的做法），
> 这是另一个量级的工程。所以业界现在实践是两层叠加：
> **约束解码保证语法 + schema 校验与反馈保证语义**。
>
> 而且约束越严，模型的"表达空间"越小，有时会牺牲推理质量 ——
> 这也是为什么不是所有场景都该上最严格的约束。

### D3. 你怎么测试一个"前缀可行性判定"？

> 三个层次：
> 1. **正向**：`{`、`{"a":`、`tru` 这些必须是 viable；`{}`、`[1,2]` 必须是 complete；
> 2. **反向**：`{]`、`nope`、`{"a": 1}}` 必须是 invalid；
> 3. **不变式**：掩码里留下的每个 token，拼上去之后必须仍然是可行前缀。
>    这条最重要，因为它不依赖我手工列的例子。
>
> 写这个模块时我踩了两个 bug：`-` 和 `12.` 被判成 `complete`（都不是合法 JSON）。
> 修法是数字解析里显式要求"整数部分至少一位数字""小数点后至少一位数字"，
> 缺了就在输入末尾抛 `_Incomplete`、在非数字处抛 `_Invalid`。

## E 类 · 与其它项目的关系

### E1. 这个项目和你的 Agent 项目怎么配合？

> 边界很清楚：
> - `mini-react-agent` 是 Agent 循环，它需要解析模型的 tool_calls；
> - `tool-forge` 是工具层，它需要校验工具参数；
> - 这个 `structured-output` 解决的是**中间那段**：怎么稳定地从模型文本里拿到结构化数据，
>   以及拿不到时怎么办。
>
> 实际对接点：`mini-react-agent` 的文本 ReAct 模式里那个正则解析器，
> 可以直接换成这里的 `extract_json`；它的工具参数校验可以换成这里的 `validate`。

### E2. 三个项目为什么不做成一个？

> 因为它们的**故障模式完全不同**，混在一起就没法独立测试：
> - 循环的问题：死循环、步数失控
> - 工具层的问题：下游超时、重试风暴、副作用重复
> - 结构化输出的问题：格式坏法、语义错误
>
> 分开的好处是每个仓库的测试都能做到"零依赖、秒级、确定性"。
> 如果合成一个，我得跑起整个 Agent 才能测一个 JSON 解析函数。
